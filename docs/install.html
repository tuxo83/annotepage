How the loop closes

One rule, and everything else follows

The client is a classic <script> tag. Not an import, not a module. It reads its whole configuration from its own tag — the server address, the project id, the version your site is running — through document.currentScript.

So import 'annotepage-client' and <script type="module"> both leave it inert. document.currentScript is null in both cases, and rather than guess an API address from nothing, the client returns and does nothing at all. No error, no console warning: it simply is not there.

Which reduces every framework to a single question: which file writes the final <body>?

One second to check it landed. Open the console on the page and run document.querySelector('script[data-project]'). A tag means the client saw itself; null means it never ran.

Where the tag goes

The tag itself is the same everywhere — the one the landing page generates for you, with your own project id. Only its address in your repository changes. 

<script src="https://cdn.jsdelivr.net/npm/annotepage-client@2/dist/annotepage.js"
        data-server="https://api.annotepage.com/api.php"
        data-project="<yours, from the landing page>"
        defer></script>
  • Nothing in it is yours to fill in except the project id, and the landing page generates that with the key it comes from.
  • data-server is the free shared server. Point it at your own instead if you would rather the encrypted blobs sat on your own disk — that is the only line that changes.
  • @2 takes fixes on its own. The locked tag does not, and says why that is a choice rather than an oversight.

These are the usual addresses, not measurements — layouts get moved. What is measured is the rule above: whatever the framework, the tag has to reach the browser as a classic script. If your framework injects it from JavaScript instead of writing it into the HTML, run the one-line check and you will know in a second.

A tag your site already knows the version of

data-version is the one attribute worth wiring to something real. When the assistant marks a note resolved, it stamps the version the fix ships in and compares it with this one: equal means resolved and online, and the note folds into the history; different means resolved, not deployed yet, and the note stays in front of the reviewer — because the defect is still on their screen. Leave it out and every fix reads as not deployed.

the version, from wherever your build already knows it 
data-version="1.4.13"                        <!-- a literal, if you deploy by hand -->
data-version="{{ app.version }}"             <!-- Twig, ERB, Blade, Django: your own variable -->
data-version={process.env.NEXT_PUBLIC_VERSION}  <!-- anything your bundler substitutes -->

The full attribute list — data-path, data-domains, data-environment, data-mode, data-labels — is in the client README.

Open, or private

The notes are encrypted either way. What changes is who holds the key — and that is one attribute of the tag.

Open: the key is in the tag

This is the tag the landing page hands you. Anyone who can open the page can read the notes and add their own, because the key is served with the page. Nothing to hand out, nothing to lose. 

data-key="<43 characters, generated for you>"

The server still cannot read anything: the key is in the page, and the page is the one thing it never receives. What it stores stays an envelope it cannot open.

The key gives reading AND writing — this format has no reader-only role. On a staging site behind a login that is your team. On a public page it is everyone, and a tag copied out of your source writes into your project.

Private: the tag carries only the project id

Each reviewer pastes the key once, in their own browser, and the tool remembers it for that site. Until it is there the client fetches nothing and decrypts nothing. Somebody who can open the page still cannot read a word. 

data-project="<22 characters, derived from the key>"

Never write both. A tag carrying a key and an id that disagree is refused, and no winner is picked — the mistake is in the page, so there is nothing to type your way out of.

The choice is the tag, and it cannot be changed later. The project id is the key hashed, so the other mode is a different key, a different id, and a different tag on every annotated page. Notes written under one do not move to the other.

The locked tag, and why the short one is not it

The tag the landing page hands you ends in @2. That is a moving target: jsDelivr resolves it to the newest 2.x, so a fix reaches your site without you touching anything. It also means the file can change under you, and there is exactly one way to prevent that.

A range and a fixed digest cannot both hold. Subresource Integrity pins the bytes: the browser hashes what it received and refuses to run anything else. Pin the bytes and the tag can never update; let it update and the digest is wrong the day it does — and a wrong digest is a silent failure, the script simply never runs, with nothing on the page and nothing in the logs to say why.

This project chose the short tag, and the reason is not about us: pinning costs nothing to whoever ships the releases, and everything to whoever pasted a tag once and will never come back to edit a digest and a version number. A fix has to reach a site whose owner has stopped thinking about the tool. Both answers stay defensible, and the other one is right here for anybody who wants it:

  • The short tag takes fixes on its own. What it gives up: if the npm account or the CDN were ever compromised, whatever they served would run on the pages carrying it. This client reads the notes in the clear in the browser, so that is not a small thing.
  • The locked tag cannot be tampered with, and cannot improve either. You update it by editing the version and the digest, both of which are in every release.
the locked tag — pinned bytes, manual updates 
<script src="https://cdn.jsdelivr.net/npm/annotepage-client@2.5.0/dist/annotepage.js"
        integrity="sha384-zopsMVKI88YIkKUGjIgfsajeAEnObuHRo3B1woLG1AabTT32SQmgywnWLkb6Z+6I"
        crossorigin="anonymous"
        data-server="https://api.annotepage.com/api.php"
        data-project="<your project id>"
        defer></script>

crossorigin="anonymous" is there only to make the digest checkable across origins; without integrity it does nothing, which is why the short tag has neither.

Every release publishes its digest, and the packages are published straight from the repository with npm provenance attestations — so the bytes on the CDN can be traced back to the commit and the workflow that built them, whichever tag you use.

One attribute the short tag also dropped

data-version is not the tool’s version, it is yours — the version your site is running. It is what lets a resolved note say resolved and online rather than resolved, not deployed yet, and without it every fix reads as not deployed, so the note stays in front of the reviewer. It is left out of the tag on the landing page because a first tag should have nothing in it you have to think about; wire it to something real once the tool is in.

Running the server yourself

The shared server at api.annotepage.com is free and open to everyone, and it never sees anything readable. Run your own anyway if you would rather the encrypted blobs sat on your own disk. It is one PHP file to upload.

1. Put annotepage-install.php anywhere under your web root — FTP, SFTP, the host’s file manager. It is the only file you upload.

the one file 
https://raw.githubusercontent.com/tuxo83/annotepage/main/server/annotepage-install.php

2. Open it in a browser. It shows one button. Pressing it downloads the rest of the server over HTTPS and checks every file against the release’s MANIFEST, one SHA-256 each, after it lands and before it is put in place. One bad hash abandons the whole thing and leaves the directory exactly as it was.

3. Answer two questions — the storage, and whether the server may update itself. Both already carry the answer that works. It needs no JavaScript.

4. Paste the line it prints into your tag:

what it prints at the end 
data-server="https://<site>/<where-you-put-it>/api.php"

Then delete annotepage-install.php. The last screen offers to delete it for you and says whether it managed.

What it needs: any server that runs PHP 7.4 or newer, with json and mbstring, and one of pdo_sqlite (compiled into PHP nearly everywhere, needs nothing else) or pdo_mysql. No dependency, no build step, no archive to extract — shared hosting often has neither zip nor phar.

The one-file route needs one thing more: a way out to HTTPS, either the curl extension or allow_url_fopen with openssl. Without it, copying the webroot/ directory installs exactly the same server, and the installer says so rather than failing halfway.

Everything else about the server — MySQL, updating it, letting it update itself, retention, rate limits, the domain lock, forcing HTTPS, what it learns anyway — is in INSTALL.md. What it can and cannot see is at the end of this page.

Localhost, staging, and the copy of the site nobody else can reach

It works with no configuration at all. localhost is a secure context, so the browser gives the client the crypto it needs. There is nothing to declare and nobody to ask.

One thing is worth knowing before you use the same project for both. A note is filed against the path of the page — not the scheme, not the host, not the port. So localhost:3000/pricing and yoursite.com/pricing are, to annotepage, the same page. Sometimes that is exactly what you want: annotate it locally, see the note again in production. Sometimes it is not.

Use a second project, with its own key, for local work if you want them apart — and never put a localhost origin in a project’s domain list on a shared server. Measured: http://localhost:3000 is the same string on every machine on earth, so declaring it admits writes from all of them.

The assistant side

The same two commands wherever you install the client. The MCP server and the command line read the same notes.

plug it in 
npm install -g annotepage-mcp
claude mcp add annotepage -- annotepage-mcp

That is the whole of it for an open project: the key is on the page, and the assistant reads it off the page you name.

A private project gives it the key, in that same command. There is no second step and nothing to write by hand.

plug it in, private project 
claude mcp add annotepage \
  -e ANNOTEPAGE_API=https://staging.example.com/notes/api.php \
  -e ANNOTEPAGE_KEY=<the 43 characters the setup screen showed you> \
  -e ANNOTEPAGE_AUTHOR=Assistant \
  -- annotepage-mcp

The key stays on your machine and never enters the conversation — it is the server that holds it, not the assistant. It does land in your shell history, and it covers one project.

Several sites, several keys: a file holds them, and you do not have to write it. Tell your assistant the site and the key once per site, and it writes the file for you.

Writing that file yourself is better, and it is still there in the MCP README: a key given in a conversation has crossed a model provider's logs, and there is no key rotation. The trade is yours to make, and it buys this — each project is named after its site, so from then on you name the site you are looking at, never a project. Any MCP client works, the command to register being annotepage-mcp over stdio.

Where the notes live, and who can read them

This page has made you choose twice — open or private, and the shared relay or a server of your own. This is what those two choices actually decide. Either way the notes are encrypted in the browser by default, and whoever runs the server — including you — cannot read the review.

Key lost = notes lost. The key is the only secret of the project. It never leaves the browser, the server receives it in no form whatsoever, and nobody can give it back to you — no recovery, no security question, no escrow. There is no rotation either: a leaked key means starting a fresh project and abandoning the notes already written. This is the cost of the sentence above, and it is not negotiable away.

One secret, three keys

HKDF-SHA-256 derives everything from the 256-bit key: the public project id (22 characters), the AES-256-GCM key, and an HMAC key for the page index. One secret to manage, and it never leaves the browser.

Grouped without being read

The server groups pages by a blind index: the first 16 bytes of an HMAC of the path, which it cannot invert. It nests replies, dates writes and sorts open from resolved without opening anything.

Everything observed, sealed

Not just the text. Encrypting the remark alone would hand over the site's tree, its wording and the list of its reviewers — and a staging site is precisely what has not been published yet.

The domain is not in the key

The day staging becomes production, the notes stay readable. Each reviewer pastes the key once more on the new domain; the notes themselves do not move.

What goes out is an AES-256-GCM envelope: the text, but also the page, the selector, the excerpt, the name, the version, the environment and the viewport. What comes back is pinned to the element again by its selector and its fingerprint — and when the element has really changed, the note is listed as an orphan rather than pinned to the wrong thing.

What the server sees anyway

Encrypting the fields is not invisibility. An operator must be able to read this without feeling betrayed, and you must know it before choosing where to put the server.

  • The number of projects, and of notes in each.
  • The number of distinct pages annotated, and the notes per page: a page that collects forty remarks is visible.
  • The time of every write, hence the rhythm of the review and the date of the last note.
  • The shape of the threads, and the fix rate and delay, through the resolution dates.
  • The approximate length of every remark: the size of the envelope gives it away to within a few bytes. It is not masked.
  • The IP address and user agent of every reviewer, like any HTTP server.
  • On a shared server, the domain of the site under review, through the Origin header the domain lock has to read. The promise is not “it does not know which site you are reviewing”; it is “it can read neither your paths, nor your names, nor your remarks”.

The domain lock is an anti-abuse measure, not an XSS defence. It stops another site consuming a project id found in the source of a page. An XSS runs inside the target page, so with the legitimate origin: it goes through the lock without effort, and it reaches localStorage anyway — hence the key. The XSS defence is elsewhere: the tool assigns text through textContent and never parses it as markup, and a check in npm run check enforces it.

What it deliberately does not do

These are choices. Saying them is more useful than discovering them later.

  • No accounts, no login. The name typed in is a convenience, not an identity. The project id is a bearer token: whoever has it can read and write — and in encrypted mode, what they read is useless without the key.
  • No moderation, and nobody can delete. A note that is posted stays; the only state it can change is resolved, and that can be taken back. A remark one can erase is a remark one can no longer contradict. The single exception is age: a server may be set to expire whole threads once their last message passes a given number of days — a public relay needs a ceiling on what it stores. Nobody chooses which, and a server that does it says so in the header of every export.
  • No way to annotate a site you cannot edit. The tag has to be in the page, so the tool is a property of the site and not of the reader.
  • No notifications. Nobody is told that a note has arrived.
  • No key rotation, and no channel for handing the key to the second reviewer.
  • No overview across pages. Open a page, or read the export.
  • No screenshots attached to a note — weighed, and not settled: the reasons are written down in the roadmap.

What it needs to run at all

What it requires, and nothing else: a recent browser in a secure context — https, or localhost. Without one the browser does not provide WebCrypto, and the tool can neither encrypt nor even compute the page index; it says so on screen rather than pretending. And a reachable annotepage server.

Where the client itself comes from is the other half of this. A file swapped at the CDN’s host runs inside your page, with access to localStorage — hence to the key. That trade, and the pinned tag that closes it, are in the locked tag above.
